# 파일 업로드 설계 및 고려사항

## 1. 검증/보안 관점

### 1-1. 확장자만 믿어도 되는가? — 실제 파일 내용·매직 넘버와의 불일치

- **고려한 점:** 실행 파일의 이름을 `report.jpg`로 바꾸면 확장자 차단만으로 탐지할 수 없다. 확장자 검사는 관리자가 정한 이름 기반 정책을 적용하는 수단이며 악성 파일 판별 기능은 아니다.
- **구현 범위:** DB에 등록된 차단 확장자를 서버에서 검사한다. 파일 시그니처·매직 넘버·악성코드 검사는 구현하지 않았다. 지원 형식별 판별 규칙과 별도 검사 운영까지 범위가 커지므로 이번 과제에서는 한계를 명시하는 것으로 정했다.
- **추가 보완 방향:** 서비스에서 허용할 파일 형식을 먼저 한정하고, 확장자·신뢰할 수 있는 내용 판별 결과를 함께 검증하면 보완할 수 있다. 필요하면 악성코드 검사와 격리 저장 후 승인하는 절차를 추가한다. 매직 넘버가 일치하는 것만으로 악성 여부까지 보장하지는 않는다.

### 1-2. 대소문자 / 이중·다중 확장자

- **고려한 점:** 대소문자를 구분하거나 마지막 확장자만 확인하면 `file.EXE`, `file.exe.txt`로 차단 정책을 우회할 수 있다. 모든 후보를 검사하는 방식은 정상적인 이름도 보수적으로 차단할 수 있다는 비용이 있다.
- **구현 범위:** 서버에서 `Locale.ROOT`로 소문자화하고 확장자 후보를 모두 검사한다. `file.PDF`는 `pdf`, `file.exe.txt`는 `exe`·`txt`, `archive.tar.gz`는 `tar`·`gz`를 검사한다. dotfile 규칙에 따라 `.tar.gz`는 첫 이름 부분인 `tar`를 제외하고 `gz`를 검사한다.
- **추가 보완 방향:** 허용 파일 형식이 정해지면 다중 확장자의 허용 조합과 내용 판별을 함께 정의할 수 있다. 규칙을 변경할 때는 기존 차단 우회·정상 파일 사례를 모두 회귀 테스트해야 한다.

### 1-3. 확장자 없는 파일, dotfile, 매우 긴 파일명

- **고려한 점:** `README`와 `.env`를 모두 차단하면 정상 사용을 제한할 수 있다. 반대로 확장자가 없다고 내용이 안전한 것은 아니며 `.env`에는 비밀 정보가 포함될 수도 있다. 긴 파일명은 DB와 운영체제의 제한도 고려해야 한다.
- **구현 범위:** `README`, `.env`, `.gitignore`는 확장자 없음으로 허용하고 `.env.exe`는 `exe`를 검사한다. 파일명은 Java `String.length()` 기준 255까지 허용하며, 빈 이름·경로 구분자·콜론·제어문자·앞뒤 공백·끝의 점 등을 거부한다. 255/256 길이 경계를 테스트했다.
- **추가 보완 방향:** 서비스 성격에 따라 dotfile과 확장자 없는 파일을 제한할 수 있다. Unicode 정규화, UTF-16 길이와 사용자 인식 문자 수의 차이, 운영체제별 예약 이름 처리도 명시하면 기준을 더 일관되게 만들 수 있다. 다운로드를 추가할 경우 파일 내용의 민감성과 접근 권한을 별도로 검증한다.

### 1-4. 확장자 입력값 검증과 정규화

- **고려한 점:** `sh`, `SH`, `.sh`, 앞뒤 공백이 있는 입력을 서로 다르게 저장하면 중복 및 정책 비교 오류가 발생한다. 과도한 자동 교정은 사용자가 의도하지 않은 값을 등록할 수 있다.
- **구현 범위:** 앞뒤 공백 제거 → 소문자 변환 → 선행 점 하나 제거 후 영문·숫자만 허용한다. ` .SH `는 `sh`로 저장하지만 내부 공백, 특수문자, Unicode 확장자와 `..sh`는 거부한다. 정규화한 값에 20자 제한을 적용하고, 빈 입력도 거부한다.
- **추가 보완 방향:** 필요한 형식이 늘어나면 허용 문자 정책을 명시적으로 확장한다. Unicode 확장자를 허용하려면 정규화와 유사 문자 처리 기준을 먼저 정하고 클라이언트·서버의 동일 입력 테스트를 추가한다.

### 1-5. 서버 사이드 검증의 필요성

- **고려한 점:** 브라우저 검증은 API 직접 호출로 우회할 수 있고, 화면을 연 이후 다른 탭에서 정책이 변경될 수도 있다.
- **구현 범위:** 프론트엔드는 즉시 안내용으로 검증하고 서버가 DB 정책으로 다시 판단한다. 로컬 브라우저에서 파일 선택 후 다른 탭에서 차단 정책을 변경했을 때 서버가 거부하는 것을 확인했다. MockMvc로 프론트엔드를 거치지 않는 요청도 검증했다.
- **추가 보완 방향:** 인증·정책 변경 권한과 요청 빈도 제한을 추가하면 공개 서비스의 통제 범위를 넓힐 수 있다. 서버 검증은 접근 제어를 대체하지 않으며, 두 기능을 별도로 적용해야 한다.

### 1-6. 업로드 파일 크기 제한 / 파일 개수 제한

- **고려한 점:** 큰 파일과 많은 파일은 메모리·임시 디스크·저장 공간을 소모한다. 애플리케이션에서 개수를 검사하기 전에 multipart 데이터가 이미 수신될 수 있다.
- **구현 범위:** DB의 전역 설정으로 파일당 크기와 요청당 개수를 제한한다. 스키마 초기값은 10 MiB·10개다. 별도로 multipart 기본 상한은 파일당 100MB·전체 요청 110MB이며 환경 변수로 조정한다. 저장 스트림의 실제 바이트 수도 검사하고 0 byte 파일은 거부한다. DB 정책과 전송 상한은 자동 연동되지 않는다.
- **추가 보완 방향:** 설정 화면의 허용 범위를 전송 상한과 맞추고, 사용자별 총 저장량·동시 업로드 수·시간당 요청량을 제한하면 자원 고갈 위험을 줄일 수 있다. 프록시 본문 제한·타임아웃과 임시 디스크 용량도 함께 관리해야 한다.

### 1-7. 원본 파일명 사용 위험과 대응

- **고려한 점:** 원본 파일명을 저장 경로로 사용하면 `../` 등의 경로 조작, 이름 충돌, 기존 파일 덮어쓰기 위험이 있다. 실행 가능한 위치에 저장하는 것도 별도 위험이다.
- **구현 범위:** 파일명에 경로 문자가 포함되면 거부하고, 실제 저장명은 서버가 생성한 UUID를 사용한다. `CREATE_NEW`로 덮어쓰기를 막으며 업로드 디렉터리를 애플리케이션의 정적 파일 경로로 공개하지 않는다. 원본명은 메타데이터로만 보관한다. 동일 원본명과 경로 조작 입력을 테스트했다.
- **추가 보완 방향:** 배포 저장소를 웹 루트·실행 경로와 분리하고 전용 최소 권한으로 운영한다. 객체 저장소를 도입할 경우 비공개 객체와 제한된 접근 URL을 사용하며, 다운로드 시 권한 검사와 안전한 응답 헤더를 추가하면 보완할 수 있다.

### 1-8. MIME 타입 스푸핑

- **고려한 점:** multipart의 Content-Type은 클라이언트가 지정하므로 실제 파일 형식을 증명하지 못한다.
- **구현 범위:** 클라이언트 MIME을 차단 판단에 사용하지 않으며 메타데이터에는 `application/octet-stream`을 기록한다. `image/png`으로 전송한 차단 확장자도 서버가 거부하는 것을 테스트했다. 이 값은 실제 내용 분석 결과가 아니다.
- **추가 보완 방향:** 서버의 내용 판별 결과와 허용 형식을 비교하고 불일치 시 거부 또는 격리하는 정책을 추가할 수 있다. 전달받은 MIME과 판별 MIME을 저장한다면 출처를 구분해야 한다.

## 2. 정책/데이터 관점

### 2-1. 고정 확장자와 커스텀 확장자가 겹치는 경우

- **고려한 점:** `exe`가 두 영역에 있으면 어떤 정책을 변경해야 하는지 불명확하고 차단 여부도 충돌할 수 있다.
- **구현 범위:** 한 테이블에서 유형을 구분하며 확장자 전체에 UNIQUE 제약을 적용한다. 비활성 고정 확장자도 커스텀으로 등록할 수 없다. 서버 사전 조회와 DB 제약으로 중복을 방어하고 `DUPLICATE_EXTENSION`으로 안내한다.
- **추가 보완 방향:** 정책 유형을 늘린다면 중복 허용 범위와 우선순위를 먼저 정의한다. 현재처럼 전역에서 한 확장자를 한 번만 관리하는 범위에서는 별도 우선순위 엔진이 필요하지 않다.

### 2-2. 정책 변경 이력/감사의 필요 여부

- **고려한 점:** 정책 변경은 이후 업로드 허용 여부에 영향을 주므로 실제 운영에서는 누가 언제 무엇을 바꿨는지 확인할 수 있어야 한다.
- **구현 범위:** 생성·수정 시각과 정책 변경 성공 로그는 있지만, 인증 사용자를 식별하는 감사 이력 테이블은 없다. 현재 인증 없는 전역 정책 데모이므로 변경자 추적을 구현한 것으로 보지 않는다.
- **추가 보완 방향:** 인증·관리자 권한을 먼저 추가한 뒤 변경자, 대상, 이전/이후 값, 시각, 요청 ID를 기록하면 원인 추적과 복구 판단을 보완할 수 있다. 감사 기록의 보관 기간과 열람 권한도 함께 정한다.

### 2-3. 200개 / 20자 제한의 근거와 초과 시 UX

- **고려한 점:** 두 값은 성능 측정으로 도출한 수치가 아니라 원 과제의 명시적인 요구값이다. 프론트엔드에서만 막으면 직접 API 호출로 초과할 수 있다.
- **구현 범위:** 정규화 후 20자, 커스텀 200개를 서버에서 제한한다. 화면은 현재 개수/200과 길이 안내를 제공하며 한도에 따라 입력·추가 버튼을 제한한다. 20/21자와 실제 DB 등록 200/201개 경계를 테스트했다.
- **추가 보완 방향:** 제품 정책상 변경 가능해야 한다면 제한값의 관리 위치를 통일한다. 여러 사용자가 동시에 마지막 자리를 등록하는 실제 경쟁 테스트와 한도 도달 화면 검증을 추가하면 신뢰도를 높일 수 있다.

### 2-4. 대량 확장자 조회/저장 시 성능·인덱스

- **고려한 점:** 정책 규모에 비해 과도한 캐시·인덱스는 관리 비용과 정합성 문제를 늘릴 수 있다. 현재 최대 규모는 고정 7개와 커스텀 200개다.
- **구현 범위:** 전체 정책 조회와 확장자 UNIQUE 인덱스를 사용한다. 업로드 시 차단 목록을 Set으로 변환하고 별도 캐시·페이지네이션·유형 인덱스는 추가하지 않았다. 커스텀 등록·삭제는 공통 설정 행을 잠근 뒤 개수를 확인하고 변경한다.
- **추가 보완 방향:** 정책 수나 트래픽이 커지면 쿼리 실행 계획·응답 시간·잠금 대기를 측정한 뒤 인덱스와 잠금 대상을 조정한다. 캐시는 정책 버전과 무효화 전략까지 함께 설계해야 한다.

## 3. UX/예외 관점

### 3-1. 차단 시 사용자 메시지 — 무엇이 왜 막혔는가

- **고려한 점:** ‘업로드 실패’만 표시하면 사용자가 어떤 파일을 수정해야 하는지 알 수 없다. 다중 파일에서는 대상 식별이 특히 중요하다.
- **구현 범위:** 차단 응답에 파일명·확장자와 `BLOCKED_FILE_EXTENSION`을 포함한다. 예: `sample.exe 파일은 차단된 exe 확장자이므로 업로드할 수 없습니다.` 중복·크기·개수 등의 오류도 구분한다. 서버 차단 상세가 없던 문제를 수정하고 API 회귀 테스트로 확인했다.
- **추가 보완 방향:** 여러 파일의 오류를 한 번에 확인해야 한다면 파일별 검증 결과를 수집하는 응답을 추가할 수 있다. 현재는 먼저 발견한 오류를 반환하며, 수정 후 상세 메시지의 브라우저 재검증은 별도 확인 대상이다.

### 3-2. 로딩/에러/네트워크 실패 상태

- **고려한 점:** 처리 중 중복 클릭은 중복 요청을 만들고, 응답이 늦거나 없을 때 사용자가 성공 여부를 오해할 수 있다.
- **구현 범위:** 조회·저장·업로드 중 상태를 표시하고 관련 버튼을 비활성화한다. 오류 메시지를 공통 처리하며 응답이 없으면 대체 안내를 표시한다. 업로드 자동 재시도는 하지 않는다. Axios의 요청 제한 시간은 10초다.
- **추가 보완 방향:** 대용량 업로드의 진행률·취소·적절한 타임아웃을 추가할 수 있다. 오프라인·지연·응답 유실을 주입하는 테스트로 화면의 복구 가능성을 검증하면 보완된다. 재시도 기능은 중복 저장을 막는 멱등성과 함께 설계한다.

### 3-3. 저장 실패 시 화면과 DB의 일관성

- **고려한 점:** 화면에서 먼저 성공 상태를 표시하면 서버 실패 시 실제 DB와 달라질 수 있다. 응답을 받지 못했다고 DB 저장이 반드시 실패한 것도 아니다.
- **구현 범위:** 정책 변경 성공 후 목록을 다시 조회하고 요청 실패를 성공으로 표시하지 않는다. 다만 저장 성공 후 재조회 실패 시 이전 목록이 남을 수 있다. 파일은 전체 검증 후 저장하고 DB 롤백 시 생성 파일을 정리한다. 두 저장소의 완전한 원자성을 보장하는 것은 아니다.
- **추가 보완 방향:** 재조회 실패 시 ‘저장 결과 확인 필요’ 상태와 재조회 버튼을 제공하면 사용자의 판단을 도울 수 있다. 요청 식별자 기반 멱등성, DB·파일 대조 작업을 추가하면 응답 유실·장애 이후 정합성도 보완할 수 있다.

### 3-4. 접근성/반응형 — 선택 사항

- **고려한 점:** 마우스 사용이나 넓은 화면을 전제로 하면 일부 사용자는 설정과 업로드 기능을 이용하기 어렵다.
- **구현 범위:** 입력·삭제 버튼의 접근성 이름, 길이 오류 안내, 모바일 화면용 스타일을 적용했다. 파일 선택 버튼도 제공한다. 스크린리더·다양한 기기에서의 전체 접근성 검증은 수행하지 않았다.
- **추가 보완 방향:** 키보드만으로 모든 기능을 사용할 수 있는지, 포커스 이동·오류 안내·색상 대비·확대 화면을 점검한다. 긴 파일명, 200개 확장자, 작은 화면의 레이아웃 테스트까지 추가하면 보완할 수 있다.

## 4. 운영 관점

### 4-1. 새로고침/동시 편집 시 정합성

- **고려한 점:** 상태를 브라우저에만 두면 새로고침 시 사라지고, 동시 등록은 개수 제한을 넘길 수 있다. 동일 설정을 동시에 편집하는 문제는 단순 저장 순서 보호와 구분해야 한다.
- **구현 범위:** 정책을 DB에 저장하고 화면 진입 시 조회한다. 새로고침 유지와 정책 변경 후 서버 차단을 확인했다. 커스텀 변경은 공통 행 잠금으로 직렬화하고 UNIQUE 제약을 둔다. 같은 설정을 여러 사용자가 바꾸면 나중에 반영된 값이 남으며 충돌 알림은 없다. 업로드 검증 이후 변경은 진행 중인 요청에 소급하지 않는다.
- **추가 보완 방향:** 실제 동시 요청 테스트로 200개 제한과 잠금 영향을 검증하고, 버전 기반 낙관적 잠금으로 오래된 화면의 수정 충돌을 안내할 수 있다. 엄격한 즉시 정책 적용이 필요하면 검증·저장 사이의 정책 버전 확인도 설계해야 한다.

### 4-2. 로그/모니터링에서 무엇을 남길 것인가

- **고려한 점:** 성공 여부뿐 아니라 실패 원인을 구분할 수 있어야 한다. 반면 파일명·내용·경로를 무분별하게 기록하면 민감 정보 노출 위험이 있다.
- **구현 범위:** 업로드 성공은 커밋 후 기록하고, API 업로드 실패는 INFO 수준에서 HTTP 상태·오류 코드를 기록한다. 확장자 차단, 정책 변경 성공, 저장·롤백 정리 실패도 서버 로그에 남긴다. 공통 업로드 실패 로그에는 사용자 파일명을 넣지 않는 것을 테스트했다. 내부 저장 오류 로그는 운영 진단 정보를 포함할 수 있으므로 공개 응답과 구분한다. 로그 수집·알림·파일 회전 정책까지 구현하지는 않았다.
- **추가 보완 방향:** 요청 추적 ID, 성공률·실패 코드별 건수·응답 시간·디스크 사용량을 수집하고 임계치 알림을 추가한다. 로그 보관 기간·접근 권한·마스킹과 정책 감사 기록을 별도로 정하면 운영 대응을 보완할 수 있다.

### 4-3. 향후 확장 — 사용자별 정책·화이트리스트

- **고려한 점:** 전역 blocklist는 과제 요구에 맞지만 사용자·업무별 허용 형식이 다른 서비스에는 부족할 수 있다. 인증과 정책 소유권 없이 사용자별 정책만 추가하면 권한 혼동이 생긴다.
- **구현 범위:** 인증 없는 전역 정책을 사용하며, 매 업로드 요청에서 DB를 읽는다. 사용자별 정책·allowlist·분산 캐시는 제외했다. CORS는 허용 브라우저 출처 설정이며 인증이나 API 접근 제어가 아니다.
- **추가 보완 방향:** 인증·관리자 권한과 정책 소유자를 먼저 정의한다. 허용 형식이 명확한 서비스에는 allowlist와 내용 검사를 결합하고, 다중 서버에서는 객체 저장소와 정책 캐시 무효화를 추가하면 확장할 수 있다.

## 5. 추가 고려사항

### 5-1. 실제 파일 저장과 재배포 후 영속성

- **고려한 점:** 업로드 직후 저장 성공과 재배포 후 파일 보존은 다르다. DB만 남고 파일이 사라질 수도 있다.
- **구현 범위:** 현재 업로드 저장소는 별도 영속 디스크 없는 컨테이너 로컬 경로이므로 재배포 후 보존을 보장하지 않는다.
- **추가 보완 방향:** 영속 볼륨 또는 객체 저장소를 사용하고 백업·복구·재배포 후 파일 조회까지 검증한다. 중요 원본을 보관하는 서비스로 전환하기 전에 필요한 보완이다.

### 5-2. DB와 파일 시스템의 장애 복구

- **고려한 점:** DB 트랜잭션은 파일 시스템까지 원자적으로 되돌려 주지 않는다. 프로세스 강제 종료나 정리 실패로 고아 파일이 남을 수 있다.
- **구현 범위:** 롤백 시 생성 파일 삭제를 시도한다. 커밋 결과가 불명확하면 정상 파일을 잘못 삭제하지 않도록 자동 삭제하지 않고 로그를 남긴다.
- **추가 보완 방향:** 임시 저장 → 확정 상태 관리, DB·저장소 대조 작업, 정리 재시도 등을 추가할 수 있다. 강제 종료·삭제 권한 부족·커밋 실패를 주입하는 검증이 필요하다.

### 5-3. 저장 공간 고갈과 파일 수명

- **고려한 점:** 파일당 제한만으로 누적 저장량은 제한되지 않는다. 파일 삭제 API가 없는 과제에서도 운영자의 정리 정책은 필요하다.
- **구현 범위:** 저장 오류를 처리하고 서버 로그를 남긴다. 총 저장량 제한, 사전 여유 공간 확인, 보관 기간과 자동 삭제는 없다.
- **추가 보완 방향:** 데모 보관 기간과 총 용량을 정하고 사용량 경보·만료 파일 정리를 추가한다. 파일·DB 기록을 함께 정리하고 재시도 가능한 작업으로 만들면 운영 부담을 줄일 수 있다.

### 5-4. 압축 파일과 Zip Bomb

- **고려한 점:** 허용된 압축 파일 안에 차단 파일이 있을 수 있고, 압축 해제 시 원본 크기보다 훨씬 많은 자원을 사용할 수 있다.
- **구현 범위:** 업로드 파일 이름의 확장자만 검사하며 압축 해제·내부 검사·Zip Bomb 탐지는 하지 않는다.
- **추가 보완 방향:** 압축 처리가 필요한 서비스에서만 해제 후 총 크기, 파일 수, 중첩 깊이, 처리 시간과 내부 경로를 제한한다. 검사 작업을 격리하면 서버 본체에 미치는 영향을 줄일 수 있다.

### 5-5. 동일 파일 재전송과 멱등성

- **고려한 점:** 서버가 저장한 뒤 응답만 유실되면 사용자의 재시도로 같은 파일이 다시 저장될 수 있다.
- **구현 범위:** UI 선택 목록에서는 이름·크기·수정 시각 기준 중복을 제외하지만 서버 요청 간 중복 저장은 허용한다. 동일 원본명도 UUID가 달라 충돌하지 않는다. SHA-256은 저장하지만 중복 제거에 사용하지 않는다.
- **추가 보완 방향:** 요청 식별자와 결과 조회를 도입하면 안전한 재시도를 지원할 수 있다. 내용 해시 기반 중복 제거는 사용자 소유권·보관 기간까지 고려해 별도 정책으로 결정한다.

### 5-6. 검증 범위와 완료 판단

- **고려한 점:** 자동 테스트가 통과해도 기대값이 요구사항을 충분히 표현하지 못할 수 있다. 실제로 공통 오류 코드, 차단 메시지, 실패 로그의 누락을 추가 점검에서 발견했다.
- **구현 범위:** 해당 세 문제를 수정하고 오류 코드·메시지·INFO 로그의 회귀 검증을 추가했다. 2026-10-01 로컬 기록은 백엔드 46개 테스트, 프론트엔드 build·lint 통과다. 실제 MariaDB 통합 테스트와 임시 디스크 저장 검증을 포함한다. DB 변경은 롤백하지만 AUTO_INCREMENT 값은 복구되지 않는다.
- **추가 보완 방향:** 별도 테스트 DB에서 실제 동시 요청, 대용량 HTTP 전송, 네트워크 장애, 강제 종료·디스크 고갈을 검증하면 운영 신뢰도를 높일 수 있다. 모든 테스트를 수행했다고 표현하지 않고, 코드 검증·브라우저 관찰·개발자의 배포 확인 기록을 구분해 관리한다.
