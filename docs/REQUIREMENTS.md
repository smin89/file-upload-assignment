# File Upload Assignment - Requirements

## 1. 목적

본 프로젝트는 파일 확장자 차단 정책을 관리하고, 실제 파일 업로드 시 해당 정책을 서버에서 적용하는 기능을 구현한다.

단순한 화면 구현을 넘어 안전한 파일 업로드를 위해 필요한 보안, 예외 처리, 데이터 정합성 및 운영 관점의 요구사항을 함께 고려한다.

모든 고려사항을 구현하는 것을 목표로 하지 않으며, 과제 범위와 구현 비용을 고려하여 다음 세 단계로 구분한다.

- **MUST**: 이번 과제에서 반드시 구현한다.
- **SHOULD**: 가능하면 구현하며 세부 정책을 설계 과정에서 결정한다.
- **DOCUMENT**: 필요성을 인지하지만 이번 과제에서는 구현하지 않고 고려사항 및 향후 개선사항으로 문서화한다.

## 2. 기능 요구사항

### 2.1 고정 확장자 관리

- **FR-01 [MUST]** 다음 고정 확장자를 제공한다: `bat`, `cmd`, `com`, `cpl`, `exe`, `scr`, `js`.
- **FR-02 [MUST]** 고정 확장자의 최초 상태는 모두 비활성화(unchecked) 상태로 한다.
- **FR-03 [MUST]** 사용자는 각 고정 확장자의 차단 여부를 check/uncheck 할 수 있다.
- **FR-04 [MUST]** 고정 확장자의 활성화 상태는 DB에 저장한다.
- **FR-05 [MUST]** 페이지를 새로고침하거나 서버를 다시 호출해도 DB에 저장된 상태를 유지한다.
- **FR-06 [MUST]** 고정 확장자는 커스텀 확장자 목록에 중복하여 표시하지 않는다.

### 2.2 커스텀 확장자 관리

- **FR-07 [MUST]** 사용자는 커스텀 확장자를 직접 입력하여 추가할 수 있다.
- **FR-08 [MUST]** 커스텀 확장자의 최대 길이는 20자로 제한한다. Frontend와 Backend 모두 길이를 검증하며 최종 판단은 Backend에서 수행한다.
- **FR-09 [MUST]** 커스텀 확장자는 최대 200개까지 등록할 수 있으며 Backend에서 최종 검증한다.
- **FR-10 [MUST]** 현재 등록된 커스텀 확장자의 개수를 `현재 개수 / 200` 형태로 표시한다.
- **FR-11 [MUST]** 등록된 커스텀 확장자를 목록으로 표시한다.
- **FR-12 [MUST]** 각 커스텀 확장자의 삭제 버튼을 통해 확장자를 삭제할 수 있다.
- **FR-13 [MUST]** 커스텀 확장자의 추가 및 삭제 결과는 DB에 반영한다.
- **FR-14 [MUST]** 동일한 커스텀 확장자의 중복 등록을 허용하지 않는다. `sh`, `SH`, `Sh`는 모두 동일한 확장자로 판단한다.

## 3. 확장자 입력 및 정규화 정책

- **VR-01 [MUST]** 확장자는 대소문자를 구분하지 않으며 비교 및 DB 저장을 위해 lowercase로 정규화한다.
- **VR-02 [MUST]** 커스텀 확장자 입력값의 앞뒤 공백을 제거한다.
- **VR-03 [MUST]** 빈 문자열 또는 공백만 존재하는 값은 등록할 수 없다.
- **VR-04 [SHOULD]** `.exe`처럼 점(`.`)을 포함하여 입력했을 경우 `.exe → exe`로 정규화할지 오류로 처리할지 정책 단계에서 결정한다.
- **VR-05 [SHOULD]** 확장자에 허용할 문자 범위를 정의하고 특수문자, 공백, Unicode 등의 처리 기준을 정한다.
- **VR-06 [MUST]** 고정 확장자와 커스텀 확장자의 중복 등록을 방지한다. 예를 들어 `exe`는 커스텀 확장자로 다시 등록할 수 없다.

## 4. 파일 업로드

- **FR-15 [MUST]** 사용자는 실제 파일을 선택하여 서버에 업로드할 수 있다.
- **FR-16 [MUST]** 파일 업로드 시 현재 DB에 저장된 확장자 차단 정책을 적용한다.
- **FR-17 [MUST]** 차단된 확장자를 가진 파일은 서버에서 업로드를 거부한다.
- **FR-18 [MUST]** Frontend의 검증 결과와 관계없이 Backend에서 다시 확장자를 검증한다.
- **FR-19 [MUST]** 차단 대상이 아닌 파일은 정상적으로 업로드할 수 있다.
- **FR-20 [MUST]** 업로드가 거부된 경우 사용자가 이해할 수 있는 실패 이유를 반환한다.
- **FR-21 [MUST]** 정상적으로 업로드된 파일은 서버가 관리하는 저장소에 실제로 저장한다.

예시 오류 메시지:

> `sample.exe 파일은 차단된 exe 확장자이므로 업로드할 수 없습니다.`

## 5. 파일명 및 확장자 판별 정책

- **FP-01 [SHOULD]** `README`처럼 확장자가 없는 파일의 업로드 정책을 정의한다.
- **FP-02 [SHOULD]** `.env`, `.gitignore`처럼 점으로 시작하는 파일의 처리 정책을 정의한다.
- **FP-03 [SHOULD]** `archive.tar.gz` 같은 다중 확장자의 처리 방법을 정의한다.
- **FP-04 [SHOULD]** `malware.exe.txt` 같은 이중 확장자의 처리 방법을 정의한다. 마지막 확장자만 검사할지 모든 확장자를 검사할지 결정한다.
- **FP-05 [MUST]** 파일 확장자 비교는 대소문자를 구분하지 않는다.

---

## 6. 파일 업로드 보안

- **SEC-01 [MUST]** 파일 차단 정책의 최종 검증은 Backend에서 수행한다. Frontend 검증은 UX 개선용 보조 수단으로만 사용한다.
- **SEC-02 [MUST]** 업로드 가능한 최대 파일 크기를 제한한다. 정확한 값은 구현 단계에서 결정하고 설정값으로 관리한다.
- **SEC-03 [SHOULD]** 한 번의 요청에서 업로드 가능한 파일 개수를 제한한다. 단일 파일 업로드만 지원한다면 1개로 제한한다.
- **SEC-04 [MUST]** 사용자가 전달한 파일명이나 경로를 실제 저장 경로 결정에 신뢰하지 않는다.
- **SEC-05 [MUST]** 원본 파일명을 실제 저장 파일명으로 그대로 사용하지 않는다.
- **SEC-06 [MUST]** 실제 저장 파일명은 UUID 등 서버에서 생성한 안전한 식별자를 사용한다.
- **SEC-07 [MUST]** Path Traversal 공격으로 서버의 임의 위치에 파일을 저장할 수 없도록 한다.
- **SEC-08 [MUST]** 업로드된 파일은 웹 서버에서 직접 실행되지 않는 안전한 위치에 저장한다.
- **SEC-09 [SHOULD]** 업로드 파일의 MIME Type 확인 방법을 검토하되 클라이언트가 전달한 `Content-Type`만 신뢰하지 않는다.
- **SEC-10 [SHOULD]** 확장자와 실제 파일 내용이 다른 경우를 탐지하기 위한 File Signature/Magic Number 검사를 검토한다.

## 7. 파일 크기 및 이름

- **FILE-01 [MUST]** 파일 업로드 최대 크기를 설정한다.
- **FILE-02 [SHOULD]** 0 byte 파일의 허용 여부를 결정한다.
- **FILE-03 [SHOULD]** 지나치게 긴 파일명에 대한 최대 길이를 결정한다.
- **FILE-04 [MUST]** 동일한 원본 파일명을 가진 파일이 여러 번 업로드되어도 저장 파일명이 충돌하지 않아야 한다.
- **FILE-05 [DOCUMENT]** Unicode 파일명 및 Unicode normalization 문제를 고려한다.
- **FILE-06 [DOCUMENT]** Windows/Linux 등 운영체제에 따른 파일명 규칙 차이를 고려한다.

## 8. 데이터베이스 및 데이터 정합성

- **DB-01 [MUST]** 확장자 정책은 DB에 영구적으로 저장한다.
- **DB-02 [MUST]** 확장자는 정규화된 lowercase 형태로 저장한다.
- **DB-03 [MUST]** 동일한 확장자의 중복 저장을 DB `UNIQUE` constraint로도 방지한다.
- **DB-04 [MUST]** 커스텀 확장자 200개 제한은 서버에서 검증한다.
- **DB-05 [MUST]** 고정 확장자와 커스텀 확장자를 구분할 수 있어야 한다.
- **DB-06 [SHOULD]** 동시에 동일한 확장자를 등록하는 요청을 고려하고 DB UNIQUE constraint를 최종 안전장치로 사용한다.
- **DB-07 [SHOULD]** API 저장 실패 시 Frontend 상태와 실제 DB 상태가 불일치하지 않도록 한다.
- **DB-08 [DOCUMENT]** 정책 변경 이력 및 변경 사용자에 대한 Audit 기능의 필요성을 고려한다. 이번 과제에서는 인증 기능이 핵심 범위가 아니므로 별도의 Audit 시스템은 구현하지 않는다.

## 9. 사용자 경험 및 오류 처리

- **UX-01 [MUST]** 확장자 추가/삭제/변경 성공 여부를 화면에 반영한다.
- **UX-02 [MUST]** 중복 확장자 등록 시 사용자에게 원인을 알려준다.
- **UX-03 [MUST]** 20자 제한을 초과하면 사용자에게 알려준다.
- **UX-04 [MUST]** 200개 제한을 초과하면 사용자에게 알려준다.
- **UX-05 [MUST]** 업로드가 차단되면 어떤 파일이 어떤 이유로 차단되었는지 표시한다.
- **UX-06 [SHOULD]** 파일 업로드 및 정책 변경 API 호출 중 loading 상태를 표시한다.
- **UX-07 [SHOULD]** 서버 오류와 사용자의 잘못된 입력으로 발생한 오류를 구분한다.
- **UX-08 [MUST]** API 요청 실패 시 실제 DB 상태와 다른 성공 상태를 화면에 표시하지 않는다.

## 10. API 오류 처리

- **API-01 [MUST]** API 오류는 일관된 형태로 반환한다.

예:

```json
{
  "code": "BLOCKED_FILE_EXTENSION",
  "message": "차단된 확장자의 파일입니다.",
  "extension": "exe"
}
```

- **API-02 [MUST]** 예측 가능한 비즈니스 오류에 식별 가능한 오류 코드를 정의한다.

예: `DUPLICATE_EXTENSION`, `EXTENSION_LIMIT_EXCEEDED`, `INVALID_EXTENSION`, `BLOCKED_FILE_EXTENSION`, `FILE_SIZE_EXCEEDED`

- **API-03 [MUST]** 서버 내부 경로, Stack Trace 등 내부 구현 정보를 클라이언트 응답에 노출하지 않는다.

## 11. Logging 및 운영

- **OPS-01 [SHOULD]** 파일 업로드 성공/실패를 서버 로그에 기록한다.
- **OPS-02 [SHOULD]** 차단 정책으로 거부된 파일 업로드를 로그에 기록한다.
- **OPS-03 [MUST]** 서버의 실제 파일 저장 경로와 같은 내부 정보를 사용자에게 노출하지 않는다.
- **OPS-04 [SHOULD]** 확장자 정책 추가/삭제/변경에 대한 로그를 남긴다.
- **OPS-05 [DOCUMENT]** 실제 서비스에서는 누가 언제 정책을 변경했는지 Audit Log가 필요할 수 있음을 고려한다.
- **OPS-06 [DOCUMENT]** 저장 공간 부족 상황과 장애 대응 방법을 고려한다.
- **OPS-07 [DOCUMENT]** 오래된 업로드 파일의 보관 및 삭제 정책이 필요함을 고려한다.

## 12. 이번 과제에서 구현하지 않는 보안 기능

다음 항목은 실제 파일 업로드 서비스에서 고려할 가치가 있지만 과제의 핵심 범위와 구현 비용을 고려하여 기본 구현 범위에서는 제외한다.

- **OUT-01 [DOCUMENT]** Antivirus / Malware Scanner(예: ClamAV) 연동
- **OUT-02 [DOCUMENT]** 압축 파일 내부의 개별 파일 검사
- **OUT-03 [DOCUMENT]** Zip Bomb 탐지 및 방어
- **OUT-04 [DOCUMENT]** Object Storage(S3 등) 기반 저장
- **OUT-05 [DOCUMENT]** 사용자별 파일 확장자 정책
- **OUT-06 [DOCUMENT]** Whitelist/Allowlist 기반 업로드 정책
- **OUT-07 [DOCUMENT]** 분산 서버 환경에서의 정책 Cache 동기화
- **OUT-08 [DOCUMENT]** 파일 Lifecycle 및 자동 삭제 시스템

현재 과제는 blocklist 기반 확장자 정책을 구현한다. 실제 보안 수준이 높은 서비스에서는 허용 가능한 파일 형식만 정의하는 allowlist 방식도 고려할 수 있다.

## 13. 추가로 발견한 고려사항

- **ADD-01 [DOCUMENT]** 압축 파일 내부에 차단 파일이 포함될 가능성을 고려한다. 이번 구현에서는 압축 파일 내부를 검사하지 않는다.
- **ADD-02 [DOCUMENT]** Zip Bomb을 이용한 Resource Exhaustion 가능성을 고려한다.
- **ADD-03 [DOCUMENT]** 검증 완료 이후 실제 파일 저장이 실패할 가능성을 고려한다. 파일 metadata를 DB에 관리한다면 DB와 파일 저장소 사이의 정합성 문제가 발생할 수 있다.
- **ADD-04 [DOCUMENT]** 정책 확인과 실제 파일 저장 사이에 정책이 변경될 가능성을 고려한다. 이번 구현에서는 업로드 검증 시점에 조회한 정책을 기준으로 판단한다.
- **ADD-05 [DOCUMENT]** 다수의 대용량 업로드 요청을 이용한 서버 Resource Exhaustion 공격 가능성을 고려한다.
